# 리뷰어 체크리스트 (새 컨텍스트 · 읽기 전용 · 고치지 않는다)

리뷰어는 「코드 리뷰어」라는 역할로 판단하지 않는다. 아래 근거만 본다:
① 메인 세션이 붙여 준 pytest / npm 출력 원문 ② `tools/trace.py` 출력 ③ `spec/V9_ko.txt` 줄 번호 ④ 코드.
답은 번호마다 `충족 / 미충족 / 판단 불가` + 근거 한 줄(파일:줄 또는 명세 줄). 고칠 방법은 한 줄까지만. 칭찬은 쓰지 않는다.

## 1. 명세 대조
1. V-1~V-10 · T-1~T-4: 각 규칙의 required/warning, 예외 허용 여부가 REQUIREMENTS.md 표와 같은가 (V9_ko 466-479)
2. 기본 꺼 둠(G3 · G5 · M-6)이 실제로 기본값에서 꺼져 있는가 (app/config.py → ValidateOptions 까지 이어지는가)
3. F-1: 검사 통과 전 편성안이 DB 에 저장되는 경로가 있는가
4. F-2 · F-4: 자동 3회 · 점장 2회를 따로 세는가, 초안 0건이 1회로 세지는가
5. F-6 · A-18: LLM 프롬프트 · MCP 결과에 employees.name 이 들어갈 수 있는 경로가 있는가
6. F-8 · F-9 · A-16: QUAL_MISSING · DOUBLE_BOOKING 을 예외 허용으로 통과시킬 수 있는가 / 승인·통지가 두 번 일어날 수 있는가
7. A-1 · A-2: 코드 오류 · 로그인 실패 응답이 사유별로 달라지는가 (달라지면 미충족)
8. A-5: 남의 점포 자원을 읽거나 바꿀 수 있는 API 가 있는가
9. A-15: 같은 thread 동시 요청이 둘 다 반영될 수 있는 경로가 있는가

## 2. 계약 일치 (병렬로 만든 모듈 사이)
10. API_CONTRACT.md 의 경로 · 요청 · 응답 · 오류 코드가 app/api 와 web/src/api.ts 에서 같은가 (다른 것을 전부 나열)
11. ReviewWait / ContactWait / resume payload 모양이 app/graph · app/runner · app/api · web 에서 같은가
12. Violation.key 를 만드는 곳이 하나(app/domain.py)뿐인가 — 다른 곳에서 따로 조립하면 waive 가 어긋난다

## 3. 운영자 관점 (이 설계를 운영해야 하는 인프라 엔지니어로서)
13. 시크릿이 코드 · compose · 로그에 값으로 들어갔는가 (.env 이름만이어야 함)
14. 프로세스가 중간에 죽으면(LLM 호출 중 · commit_notify 중) 무엇이 남고, 재시작하면 이어지는가 (근거가 되는 테스트가 있는가)
15. LLM 호출 시간 한도(F-13)가 실제로 전체 시간을 자르는가, SDK 재시도로 몇 배가 될 수 있는가
16. 이미지 · 패키지 버전이 고정돼 있는가 (latest · ^ · ~ 가 있으면 미충족)

## 4. 테스트의 질
17. 「일부러 깨뜨리는」 테스트가 실제로 실패를 잡는가 — assert 가 비어 있거나 항상 참인 테스트를 나열
18. skip / xfail / 넓은 except 로 실패가 가려진 곳을 나열
19. trace.py 의 「테스트 없음」 번호 중 MVP 시연(11/20)에 꼭 필요한 것 (V9_ko 14-22 M 번호 기준)
